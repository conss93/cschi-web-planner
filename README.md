# 웹사이트 기획 에이전트

상담 메모를 넣으면 식스샵 프로로 만들 웹사이트의 기획서를 만든다.
사이트맵, 페이지별 섹션 구성, 각 섹션에 쓸 마켓플레이스 블록, 제작 유의점까지.

외주 제작을 위한 내부 도구다. 고객에게는 결과물만 전달한다.

## 왜 이렇게 만들었나

기획서가 쓸모 있으려면 **식스샵에서 실제로 조립 가능한 구성**이어야 한다.
그래서 AI 가 화면을 상상하게 두지 않고, 마켓플레이스에 실재하는 블록 230개
안에서만 고르게 한다. 블록마다 이름·설명글·썸네일·데모 주소가 있어서
이름만 보고 찍는 것이 아니라 설명을 읽고 고른다.

블록에는 톤 계열이 붙어 있다(Calm, Fresh, Natural 등 9종). 한 계열로 통일하면
블록마다 색과 여백을 손보는 작업이 사라져 예산 안에 들어온다. 그래서
파이프라인은 톤을 먼저 정하고, 그 뒤로는 그 계열과 커뮤니티 블록만 후보로 둔다.

## 준비

Node 20 이상.

```bash
npm install
```

설정은 `.env.local` 파일에 둔다. CLI 와 웹앱이 같은 파일을 읽는다.

```bash
cp .env.example .env.local
```

터미널에서 `export` 해도 동작하지만 창을 닫으면 사라지고 셸 히스토리에 남는다.
키와 연결 문자열은 이 파일에만 두고 문서·대화·커밋에 남기지 않는다.
노출되면 즉시 발급처에서 폐기하고 새로 만든다. `.env.local` 은 커밋되지 않는다.

저장소에 들어 있는 `data/sixshop-blocks.json` 은 스냅샷이다. 마켓플레이스에
블록이 추가되거나 썸네일 크기를 정확히 맞추려면 `npm run catalog` 로 다시 만든다.

## 쓰는 법

상담 메모를 텍스트 파일로 저장하고 넘긴다. 형식은 자유다.

```bash
npm run plan -- examples/brief-tax-firm.txt
```

`out/plans/<상호>/` 에 `plan.html` 과 `plan.json` 이 생긴다.
HTML 은 브라우저로 열어 그대로 보거나 인쇄해 쓴다.

받아야 할 항목은 `data/brief-form.json` 에 정의돼 있다. 24개 항목 중 16개가
필수인데, **비어 있어도 생성을 막지 않는다.** 상담 중에 폼을 채우느라 대화가
끊기면 안 되기 때문이다. 대신 빈 항목은 가정을 명시하고 기획서 첫머리에
"확인해야 할 것" 으로 올린다.

## 파이프라인

한 번에 다 시키지 않고 단계로 나눈다. 단계마다 출력 스키마가 다르고,
앞 단계의 결론이 뒤 단계의 입력이 된다.

```
상담 메모
  → 브리프 정리      빈 항목을 가정으로 채우고 되물을 질문을 만든다
  → 전략과 톤        단일 목표, 신뢰의 재료, 스타일 계열 선택
  → 사이트맵         페이지 4~6개와 메뉴 구조
  → 페이지 구성      페이지마다 동시에. 섹션 순서와 블록 지정
  → 기능과 유의점    필요 기능, 제작 주의점, 기술 검토
  → 검증             실재하지 않는 블록을 걸러낸다
  → 기획서 HTML
```

블록 목록은 모든 단계에 똑같이 들어가므로 프롬프트 캐시 구간에 둔다.
페이지가 여러 개여도 목록은 한 번만 값을 치른다. 역할 문자열과 블록 목록이
매 호출 동일해야 캐시가 사는데, 자체 점검이 그것을 검사한다.

## 명령

| 명령 | 하는 일 |
|---|---|
| `npm run plan -- <파일>` | 상담 메모로 기획서 생성 |
| `npm run test:pipeline` | 모델 없이 파이프라인·검증·화면 점검 |
| `npm run capture` | 마켓플레이스 블록 수집 (브라우저) |
| `npm run fetch` | 마켓플레이스 API 에서 직접 수집 |
| `npm run catalog` | 수집 결과를 카탈로그로 합치기 |
| `npm run selftest` | 수집기 점검 |

## 파일

```
data/sixshop-blocks.json     블록 카탈로그 230개
data/sixshop-categories.json 카테고리·스타일 체계와 API 스키마 메모
data/brief-form.json         상담 입력 폼 정의
src/catalog.mjs              모델용 블록 목록 생성 (파일 의존 없음)
src/catalog-file.mjs         카탈로그를 파일에서 읽기 (CLI 전용)
lib/db.mjs                   기획서 저장소 (Neon Postgres)
lib/runner.mjs               웹에서 한 번에 한 단계씩 실행
app/                         웹 화면과 API
src/model.mjs                모델 호출과 캐시 구간 배치
src/pipeline.mjs             단계별 프롬프트와 스키마, 검증
src/render.mjs               기획 결과를 HTML 로
tools/marketplace-capture/   블록 카탈로그를 만드는 도구들
docs/sample-plan-tax-firm.html  손으로 만든 기획서 샘플 (기준점)
```

## 알아 둘 것

마켓플레이스 블록 설명글은 **전부 쇼핑몰 기준**으로 쓰여 있다. 상품, 컬렉션,
구매 전환을 전제로 한다. 그래서 프롬프트에 "상품을 그 업종의 서비스로 바꿔
읽으라" 를 명시한다. 이것이 없으면 모델이 "이 업종에 맞는 블록이 없다" 고 답한다.

게시판·블로그 목록을 만드는 블록과 인물 소개 전용 블록은 마켓플레이스에 없다.
전자는 식스샵 기본 게시판 기능으로, 후자는 카드 배너를 전용해 처리한다.

## 웹앱

CLI 와 같은 파이프라인을 브라우저에서 쓴다. 어느 컴퓨터에서든 접속할 수 있고,
API 키가 서버에만 있어 노출될 일이 없다.

```bash
cp .env.example .env.local   # 세 값을 채운다
npm run dev
```

| 화면 | 하는 일 |
|---|---|
| `/` | 만든 기획서 목록 |
| `/new` | 상담 폼. `data/brief-form.json` 을 그대로 그린다 |
| `/plans/<id>` | 생성 진행 상황과 완성된 기획서. 인쇄로 PDF 저장 |
| `/share/<token>` | 고객에게 보내는 읽기 전용 링크. 로그인 불필요 |

### 왜 단계마다 요청을 나눴나

기획서 하나에 몇 분이 걸리는데 서버리스 함수는 그만큼 오래 못 버틴다.
Vercel 무료 플랜은 한 요청이 60초를 넘기면 잘린다. 그래서
`/api/plans/<id>/stage` 는 **한 번에 한 단계만** 돌리고 결과를 저장한다.
창을 닫아도 상태가 남고, 진행 표시도 이 구조에서 공짜로 나온다.

페이지 구성은 페이지끼리 독립이므로 화면이 **한꺼번에 요청한다.** 순차로
돌리면 페이지 수만큼 시간이 곱해진다. 다만 동시에 끝난 결과를 각자 통째로
저장하면 나중 것이 앞선 것을 지우므로, 페이지는 한 SQL 문장 안에서 이어
붙인다. 완성 순서가 뒤섞이므로 각 페이지에 번호를 달아 두고 화면에 내보낼 때
사이트맵 순서로 되돌린다.

기능·유의점과 기술 검토도 원래 한 단계였는데 100초를 넘겨서 둘로 나눴다.

### 인증

사용자가 한 명이라 계정 체계를 두지 않았다. `PLANNER_PASSWORD` 하나와
서명된 쿠키가 전부다. 고객 공유 링크는 이 인증을 거치지 않고, 대신 추측할 수
없는 토큰을 쓴다.

### Vercel 배포

1. [neon.tech](https://neon.tech) 에서 Postgres 프로젝트를 만들고 연결 문자열을 복사한다.
2. Vercel 에서 이 저장소를 import 한다.
3. 환경변수 세 개(`ANTHROPIC_API_KEY`, `DATABASE_URL`, `PLANNER_PASSWORD`)를 넣는다.
4. 배포한다. 테이블은 첫 요청 때 자동으로 만들어진다.

**저장소를 비공개로 두어야 한다.** 기획서에 고객사 정보가 들어간다.
